JAHVI BEATSYNC LAB — COMPLETE IMPLEMENTATION SPECIFICATION
===========================================================

PROJECT:
Jahvi V2.0 Backend

FEATURE:
BeatSync Lab

IMPORTANT:
This is an implementation specification. Do not redesign the architecture,
do not add unnecessary abstractions, and do not create a complicated job/
queue system.

The goal is simple:

USER VIDEO + USER HEADSHOT TIMESTAMPS + USER MUSIC
                    ↓
              BEATSYNC ENGINE
                    ↓
        HEADSHOTS LAND ON BEATS
                    ↓
              FINAL VIDEO


===========================================================
1. FIRST: INSPECT THE EXISTING PROJECT
===========================================================

Before writing code, inspect the existing backend and the files I uploaded.

There are existing BeatSync-related files containing:

- BeatSync HTML
- BeatSync CSS
- BeatSync JavaScript
- Librosa/RMS Python logic

Do NOT throw away the existing logic.

Understand how the current frontend sends:

- video
- audio/music
- timestamps
- effect/preset information
- aspect ratio
- other BeatSync settings

Reuse existing working code wherever possible.

Do not create duplicate implementations of things that already work.


===========================================================
2. CORE BEATSYNC ARCHITECTURE
===========================================================

BeatSync should be treated as a VIDEO PROCESSING PIPELINE.

The main backend processing module should be:

    timestamp_sync.py

IMPORTANT CHANGE:

timestamp_sync.py should NOT only receive a list of timestamps.

It should receive the actual video and perform the synchronization work.

Conceptually:

    timestamp_sync.py(
        video,
        audio,
        headshot_timestamps,
        beat_timestamps,
        settings
    )

Its responsibility is to manipulate the video so that the
important headshot moments line up with the detected beats.


===========================================================
3. INPUTS
===========================================================

BeatSync receives:

A. VIDEO

The user's uploaded gameplay/edit video.

B. AUDIO

The user's selected/custom music.

C. HEADSHOT TIMESTAMPS

These come from the frontend.

Example:

    [2.15, 4.80, 7.30, 9.95, 12.40]

These represent the moments in the video where the user's
headshots occur.

D. BEAT TIMESTAMPS

These are generated by the existing Librosa/RMS logic.

Example:

    [1.92, 4.61, 7.42, 10.02, 12.31]

E. BEATSYNC SETTINGS

Use the existing frontend settings where applicable.

Do not invent unnecessary settings.


===========================================================
4. LIBROSA / RMS BEAT DETECTION
===========================================================

Reuse the existing Librosa/RMS implementation already present
in the project.

Do not create a second unrelated beat detector.

The audio should be analyzed and converted into beat timestamps.

Conceptually:

    audio
      ↓
    Librosa
      ↓
    RMS / beat analysis
      ↓
    beat timestamps


Example:

    [
        0.52,
        1.04,
        1.56,
        2.08,
        2.61,
        ...
    ]

The exact beat detection algorithm should remain compatible
with the existing implementation.


===========================================================
5. IMPORTANT: HEADSHOT → BEAT SYNCHRONIZATION
===========================================================

The purpose of BeatSync is NOT simply to play the video faster.

The purpose is:

    HEADSHOT TIMESTAMP
            ↓
    MATCH TO A BEAT
            ↓
    MODIFY VIDEO TIMING
            ↓
    HEADSHOT OCCURS ON BEAT

Example:

Original:

    headshot = 2.15s
    target beat = 2.40s

The video timing must be adjusted so that the headshot
lands at approximately 2.40s.

Another example:

    headshot = 4.80s
    target beat = 4.62s

The relevant video section must be adjusted so the headshot
lands at approximately 4.62s.


===========================================================
6. DO NOT SIMPLY SHIFT THE ENTIRE VIDEO
===========================================================

Synchronization must happen around the relevant sections.

Do NOT simply:

    video = video + global_offset

because different headshots may need different timing adjustments.

The system must preserve the ordering of the headshots.

Example:

HEADSHOTS:

    H1 = 2.15
    H2 = 4.80
    H3 = 7.30
    H4 = 9.95

BEATS:

    B1 = 2.40
    B2 = 4.62
    B3 = 7.45
    B4 = 9.81

The result should preserve:

    H1 → B1
    H2 → B2
    H3 → B3
    H4 → B4


===========================================================
7. VIDEO SEGMENTATION
===========================================================

The implementation should logically divide the video around
the headshot timestamps.

For example:

    [start → H1]
    [H1 → H2]
    [H2 → H3]
    [H3 → H4]
    [H4 → end]

These sections can then be adjusted independently so that
the headshot points land on the intended beats.

Use FFmpeg for the actual video processing.


===========================================================
8. TIMING ADJUSTMENT
===========================================================

The synchronization engine may need to:

- shorten a section
- extend a section
- speed up a section
- slow down a section
- cut/trim a section
- concatenate sections

depending on the relationship between:

    current headshot time

and:

    target beat time


Do not distort the whole video unnecessarily.

Only modify the timing needed to synchronize the sections.


===========================================================
9. BEAT COUNT VS HEADSHOT COUNT
===========================================================

The system must safely handle different numbers of beats
and headshots.

CASE A:

    headshots == beats

Normal synchronization.

CASE B:

    beats > headshots

Only use the beats necessary for the available headshots,
according to the synchronization logic.

Do NOT invent headshots.

CASE C:

    headshots > beats

Do not crash.

Handle the remaining headshots gracefully according to the
existing BeatSync design.


===========================================================
10. IMPORTANT: WHEN BEATS EXTEND BEYOND THE VIDEO
===========================================================

This is an important part of the architecture.

If the required beat timeline is longer than the available
video/headshot material, the system should be able to append
additional video material to the back.

Example:

Video material ends around:

    15.0 seconds

But the required beat timeline continues to:

    18.0 seconds

The system can append suitable video material to the end
before producing the final output.

The purpose is to ensure the final edit does not simply stop
because the music/beat timeline is longer.


===========================================================
11. DO NOT LOAD THE ENTIRE VIDEO INTO RAM
===========================================================

Jahvi runs on limited servers.

Do NOT implement:

    entire_video = read_into_memory()

Use FFmpeg file-based processing.

Work with:

- temporary files
- FFmpeg streams
- intermediate files
- chunked file handling where appropriate

Avoid unnecessarily loading large videos into Python memory.


===========================================================
12. TEMPORARY FILES
===========================================================

Every processing request must use unique temporary filenames.

NEVER use:

    output.mp4

as a shared global filename.

Use UUID-based names.

Example:

    /tmp/jahvi_<uuid>_input.mp4
    /tmp/jahvi_<uuid>_audio.mp3
    /tmp/jahvi_<uuid>_segment_001.mp4
    /tmp/jahvi_<uuid>_final.mp4

This prevents users processing videos simultaneously from
overwriting each other's files.


===========================================================
13. FINAL OUTPUT
===========================================================

The final BeatSync video should:

- contain the synchronized gameplay
- contain the selected music
- preserve the intended video quality
- preserve the requested aspect ratio
- be playable in normal browsers
- use MP4/H.264-compatible output unless the existing project
  already specifies another compatible format


===========================================================
14. AUDIO
===========================================================

The user's selected music is the main synchronization source.

Librosa analyzes the music.

The final video should contain that music.

Do not accidentally use the temporary Librosa-generated
audio as the final audio unless that is already how the
existing BeatSync implementation works.

If gameplay audio is supported by the current UI/backend,
respect the existing volume settings.

Do not invent additional audio controls.


===========================================================
15. ASPECT RATIO
===========================================================

BeatSync should support the existing three requested formats:

    TikTok
    Instagram
    YouTube

Use the existing frontend values/format.

Do not add FPS or bitrate controls to the BeatSync UI.

FPS and bitrate are NOT user-configurable BeatSync settings.


===========================================================
16. EFFECTS
===========================================================

BeatSync must remain compatible with Jahvi's effects system.

Do not hardcode a new effects system inside timestamp_sync.py.

The effect system should remain separate from synchronization.

If the pipeline requires:

    video
      ↓
    effects
      ↓
    timestamp synchronization

then preserve that architecture.

timestamp_sync.py should focus on TIMING/SYNCHRONIZATION.


===========================================================
17. PRESET COMPATIBILITY
===========================================================

BeatSync must remain compatible with Jahvi presets.

A preset may contain information such as:

- effect IDs
- effect configuration
- synchronization settings

Do not create a completely separate preset system.

Reuse the existing preset structure.


===========================================================
18. CREDITS
===========================================================

BeatSync must use the existing Jahvi credit system.

Before processing:

1. Decode/verify the user's JWT.
2. Identify the user.
3. Query the users table.
4. Check the user's available credits.
5. Reject the request if the user does not have enough credits.

Do not trust the frontend credit value.

The backend is authoritative.


===========================================================
19. CREDIT DEDUCTION
===========================================================

Credits must NOT be deducted merely because the user clicked
"Generate".

Deduct credits only after successful processing/export.

If FFmpeg fails:

    DO NOT deduct credits.

If Librosa fails:

    DO NOT deduct credits.

If synchronization fails:

    DO NOT deduct credits.

If the final file does not successfully generate:

    DO NOT deduct credits.

Only a successful export should consume credits.


===========================================================
20. AUTHENTICATION
===========================================================

Use the existing Jahvi JWT authentication system.

Do not create another authentication mechanism.

The BeatSync endpoint must:

- require a valid access token
- identify the user
- check credits
- process the request
- return the result


===========================================================
21. USER ACCESS / PLAN
===========================================================

Use the existing Jahvi access/plan logic.

Do not hardcode:

    if plan == "pro"

in random places.

Reuse the existing access-checking approach used by
the Dashboard and Headshot Extraction Lab.

If `/me` or the existing user-access endpoint is already
used by the frontend, keep that format consistent.


===========================================================
22. FILE UPLOAD SAFETY
===========================================================

Do not trust the frontend.

Validate uploaded files on the backend.

Validate:

- file exists
- file type/extension
- file size
- audio availability
- video readability

Reject invalid input cleanly.

Do not allow arbitrary filesystem paths from the client.


===========================================================
23. FFmpeg
===========================================================

Use the installed FFmpeg executable.

Do not assume MoviePy is required.

Prefer direct FFmpeg commands/subprocess calls where appropriate.

Every FFmpeg call must:

- check the return code
- capture useful stderr
- fail cleanly
- clean up temporary files


===========================================================
24. FFmpeg TIMING SAFETY
===========================================================

Be careful with:

- timestamps
- keyframes
- PTS/DTS
- frame rate
- audio synchronization
- concatenation
- variable-duration segments

Do not assume that cutting at arbitrary timestamps is always
frame-perfect.

The final result should prioritize stable playback and
correct synchronization.


===========================================================
25. VIDEO CONCATENATION
===========================================================

When multiple processed segments are created, concatenate
them safely.

All segments must have compatible:

- resolution
- codec
- pixel format
- frame rate
- audio configuration

or they must be normalized before concatenation.

Do not create a pipeline where segment 1 uses different
parameters from segment 2 and then expect FFmpeg concat to
always work.


===========================================================
26. ERROR HANDLING
===========================================================

Return useful HTTP errors.

Examples:

    400
    Invalid timestamps

    400
    Invalid audio/video

    401
    Invalid authentication

    403
    Insufficient credits / access denied

    413
    File too large

    500
    Video processing failed

Do not expose raw internal stack traces to the user.


===========================================================
27. PROGRESS
===========================================================

Use Jahvi's existing progress architecture if available.

Progress should represent real processing stages.

Example:

    10% Upload received
    20% Analyzing audio
    35% Detecting beats
    50% Preparing video segments
    70% Synchronizing timestamps
    85% Rendering final video
    95% Finalizing
    100% Complete

Do NOT fake progress by running a timer.

If the current project already has SSE/progress infrastructure,
reuse it.


===========================================================
28. NO UNNECESSARY JOB QUEUE
===========================================================

Do NOT introduce:

- Celery
- Redis queue
- RabbitMQ
- Kubernetes jobs
- complex worker architecture

unless the existing project already requires them.

For the current MVP, keep processing straightforward.

The request can execute through the existing FastAPI backend
processing architecture.


===========================================================
29. API DESIGN
===========================================================

Use the existing Jahvi router organization.

Do not randomly create:

    beatsync_service.py
    beatsync_manager.py
    beatsync_worker.py
    beatsync_engine.py
    beatsync_processor.py
    beatsync_utils.py
    etc.

just for the sake of abstraction.

Keep the implementation understandable.

The important processing module is:

    timestamp_sync.py


The API route should be thin.

Conceptually:

    POST /beatsync

Route responsibilities:

1. authenticate
2. validate input
3. check credits/access
4. save uploads
5. call processing logic
6. deduct credits after success
7. return output information


===========================================================
30. OUTPUT RESPONSE
===========================================================

Do not send the entire MP4 inside a JSON response.

Return the generated file information.

Example:

    {
        "success": true,
        "filename": "uuid.mp4"
    }

Then provide/use the existing download/streaming mechanism.


===========================================================
31. VIDEO DOWNLOAD
===========================================================

The generated video should be downloadable/streamed using
the existing Jahvi backend file-serving approach.

Do not read the entire output video into RAM.

Use streaming/chunked response behavior.

The frontend should receive the filename or output identifier,
then request the file.


===========================================================
32. CLEANUP
===========================================================

After successful download or after processing failure,
temporary files should eventually be deleted.

Never allow /tmp or uploads to grow forever.

Clean:

- temporary audio
- intermediate segments
- temporary processed videos
- failed outputs

Do not accidentally delete another user's files.


===========================================================
33. CONCURRENCY
===========================================================

Multiple users may process videos at the same time.

Therefore:

NEVER:

    output.mp4
    temp.mp4
    audio.mp3
    segment1.mp4

as shared filenames.

Always use unique UUID paths.


===========================================================
34. TIMESTAMP VALIDATION
===========================================================

Validate every user timestamp.

Requirements:

- must be numeric
- must be >= 0
- must be within/related to the actual video duration
- must be sorted or normalized
- must not contain impossible values
- must not contain NaN/Infinity

If timestamps are unordered, either sort them safely or reject
them according to the existing frontend contract.

Do not silently produce broken edits.


===========================================================
35. BEAT TIMESTAMP VALIDATION
===========================================================

Librosa output must also be validated.

Remove/ignore impossible values.

Ensure:

    beat >= 0

and beats are sorted chronologically.

If no usable beats are detected:

    return a clean error

Do not attempt synchronization with an empty beat list.


===========================================================
36. EDGE CASE: NO HEADSHOTS
===========================================================

If the user sends no headshot timestamps:

    reject the BeatSync export.

Do not generate a random beat edit.

The user must provide headshot timestamps.


===========================================================
37. EDGE CASE: ONE HEADSHOT
===========================================================

One headshot must still work.

Do not assume there are always multiple timestamps.


===========================================================
38. EDGE CASE: VERY CLOSE HEADSHOTS
===========================================================

If two headshot timestamps are extremely close together,
avoid generating invalid/negative-duration segments.

Validate segment duration before calling FFmpeg.


===========================================================
39. EDGE CASE: VIDEO SHORTER THAN REQUIRED
===========================================================

If synchronization requires more footage than the original
video contains, use the previously defined append behavior.

Do not crash simply because the beat timeline is longer.


===========================================================
===========================================================
40. DO NOT CHANGE THE FRONTEND UNNECESSARILY
===========================================================

Inspect the existing BeatSync HTML/CSS/JS.

Only modify frontend code when required to connect it to the
correct backend implementation.

Do not redesign the UI.

Do not replace working UI.

Do not introduce a new framework.

Do not change the existing visual design unless required
for functionality.


===========================================================
41. EXISTING LIBROSA FILE
===========================================================

If the uploaded Librosa/RMS Python file already exposes a
function for beat detection, reuse it.

If it currently only works as a script, refactor the MINIMUM

Do not duplicate the entire algorithm.


===========================================================
42. ARCHITECTURE FLOW
===========================================================

The intended architecture is:

USER
 ↓
BeatSyncLab frontend
 ↓
POST BeatSync request
 ↓
FastAPI authentication
 ↓
Validate user/access/credits
 ↓
Save video + audio temporarily
 ↓
Librosa/RMS analyzes music
 ↓
Generate beat timestamps
 ↓
timestamp_sync.py receives:
    video
    audio
    headshot timestamps
    beat timestamps
    settings
 ↓
Split/adjust video sections
 ↓
Synchronize headshots to beats
 ↓
Append additional video if required
 ↓
Concatenate final video
 ↓
Apply/finalize audio
 ↓
Generate final MP4
 ↓
Verify output exists
 ↓
Deduct credits
 ↓
Return filename
 ↓
Frontend downloads/streams result

43. IMPORTANT SEPARATION OF RESPONSIBILITIES
===========================================================

timestamp_sync.py:

    VIDEO TIMING + SYNCHRONIZATION

    BEAT DETECTION

    AUTH + VALIDATION + REQUEST HANDLING

    USER + CREDITS + PLAN

    USER INPUT + TIMESTAMPS + UI + PROGRESS

    ACTUAL VIDEO/AUDIO PROCESSING


Do not mix all responsibilities into one giant function.

===========================================================
47. SUCCESS CONDITION
===========================================================

BeatSync is considered successful when:

1. User uploads video.
2. User supplies/selects music.
3. User supplies headshot timestamps.
4. Librosa detects beats.
5. timestamp_sync.py receives the actual video and timestamps.
6. Video sections are adjusted.
7. Headshot moments land approximately on target beats.
8. Additional video can be appended when required.
9. Final MP4 is generated.
10. Output can be streamed/downloaded.
11. Credits are deducted only after success.
12. Temporary files are cleaned.
13. Existing Jahvi features continue working.
